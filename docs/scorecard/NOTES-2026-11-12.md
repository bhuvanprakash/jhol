## Root cause of the `express` failure (verified, not guessed)

```
$ npm view get-intrinsic dist-tags        → {"latest":"1.3.0"}
$ npm view get-intrinsic versions         → … 1.2.7, 1.3.0, 1.3.1
$ npm view get-intrinsic@1.3.1 deprecated → (none)
$ npm view side-channel-map@1.0.1 dependencies.get-intrinsic → ^1.2.5
$ npm view call-bound@1.0.4 dependencies.get-intrinsic       → ^1.3.0
```

Both dependents' ranges are satisfied by 1.3.0 **and** 1.3.1.

- **npm installs 1.3.0** — the version the `latest` dist-tag points at.
- **jhol installs 1.3.1** — the highest version satisfying the range.

1.3.1 is published but not tagged `latest`, and it is 1.3.1 that pulls `async-function` (and that,
`async-generator-function`). So one version choice explains both the extra packages and the file
count (+19 %).

**This is not a layout or installer bug. It is a version-selection policy difference**, and it is
the kind that cascades: a different `get-intrinsic` changes the tree, the file count and, for
native packages, which prebuilt binaries get pulled (`sharp` adds `@emnapi/runtime` for the same
reason).

## The rule this points to (ours, derived from the failure)

> When a range is satisfied by the version the registry's `latest` tag points at, prefer it.
> Only when `latest` does not satisfy the range, take the highest satisfying version.

Why it is right on its own terms, not because npm does it: a fresh install should reproduce what
`latest` promises. Choosing a published-but-untagged version means the tree depends on a release
the registry's own front page does not advertise — which is exactly how a fresh install differs
from the one every other tool produces.

**What this is not:** it is not porting npm's resolver. JAGR-∞ stays the resolver; this is one
preference inside candidate ordering, derived from an observed contract and provable with the
scorecard row that produced it.

## The `jest` failure is a different class

jhol installs 2 packages npm does not (`camelcase@5.3.1`, `semver@6.3.2` missing relative to npm).
Same suspicion — different version of an intermediate package eliminating or requiring a

## Harness limitations found while using it

1. **Layout is invisible.** The manifest is a *set* of `name@version`, so two nested copies of
   1.3.0 and one flattened copy look identical. A later pass should record depth, not just
   identity. (Deliberately deferred: fix resolution first, layout second.)
2. **Extra files pass.** The file check only fails when jhol has < 95 % of npm's count, so the
   `esbuild` row passed while shipping 16 files against 11. Should become an absolute comparison
   once layout is recorded.
3. **Timing is informational only.** Cold npm and cold jhol hit the network differently; the
   column stays out of the verdict until semantics match.
4. **`--ignore-scripts` means lifecycle scripts are not yet compared.** Pass 2 must run with
   scripts enabled on the scenarios that build (sharp), and compare script presence and order.

## Order of work this establishes

1. Implement the `latest`-preference rule in candidate ordering; prove it with the `express` row.
2. Re-run the scorecard; classify what remains by reading the registry, never by guessing.
3. Add depth to the manifest, then make the file check absolute.
4. Pass 2 with scripts; compare presence/order on `sharp`.
5. Then the Linux gate: `docker run … sh scripts/scorecard.sh`.

No row is deleted because it fails, and no failure is "fixed" by loosening the comparison.

## Update: the rule is implemented, and it is not yet on the path that decides

The `latest`-preference is now in `packuments::pick_for_specs` (one rule, five tests) and used by
`jagr_nest::choose_version` and both `lockfile_write::resolve_*` helpers. **`express` still
resolves `get-intrinsic@1.3.1`**, so the rule is inert for installs. Evidence, not a guess:

```
$ JHOL_TRACE_PICK=1 jhol install      # fresh dir, express@4.18.2
[pick] jagr              237 calls
[pick] pick_for_specs    239 calls
```

476 version decisions, and **not one of them is `get-intrinsic`** — so its version is chosen by a
code path that never asks these helpers. Two facts point at where:

1. The lockfile records **exact pins** in parents' dependency maps
   (`side-channel-map@1.0.1 → get-intrinsic: "1.3.1"`), not the original `^1.2.5` the registry
   publishes. So by the time anything with a range runs, the choice may already be made.
2. The resolver expands candidates from "newest version" helpers
   (`packument::newest_version`, `collect_dep_names_for`'s `newest`) rather than from a
   range-selection call.

Next step is therefore narrow and named: make **candidate expansion** latest-aware in one place
(the newest-version helpers plus the ordinal where the lattice takes its max), not to add a sixth
range-selection helper. Until the `express` row changes, this note stays open and no claim is made
that it is fixed.

Correction to the earlier plan: "implement the rule and prove it with the express row" assumed a
single selection choke point. There are several, and the instrumented trace is how that was found
rather than assumed.

## The actual cause: the solver was being fed a snapshot, and the estimate became the resolver

The `latest`-tag rule was never going to matter, because `select_versions` **returns `None`** for
an ordinary `express@4.18.2` install. Instrumented bail reasons:

```
[solve] bail: propagate: JAGR-∞ conflict: no version of mime satisfies every dependent
        (candidates after narrowing: [1.6.0]); accepts needs mime…; send needs mime…; type-is needs mime…
[solve] chart returned None for get-intrinsic
```

And the packument the solver received:

```
[solve] input packuments=70 mime_versions=Some(1)
        mime_keys=Some(["_bundled_index_synth", "dist-tags", "name", "versions"])
```

`_bundled_index_synth` is a build-time snapshot with **one version per package**. A snapshot's
`mime@1.6.0` cannot satisfy `~1.2.6` *and* `0.19.0`, so propagation reports a conflict, the solver
declines, and the comment in `install.rs` applies: *"if the chart cannot be built or the solve
fails, the estimate stands."* The greedy estimate — built from the same snapshot — chose
`get-intrinsic@1.3.1`, which is what the world saw.

So three defects compound:

1. **A snapshot was used mid-resolution** for exact pins (`bundled_index_allowed` returned true when
   every constraint was a pin), so the estimate could feed itself from a stale version set.
2. **Packument version lists were pruned by "constraints seen so far"**, dropping versions a later
   dependent needed (`mime`), which made the solver's input unsound even without the snapshot.
3. **The solver was bypassed silently.** A failing solve was not reported, so a wrong tree shipped
   with no signal.

Fixed here: the snapshot no longer answers exact pins online (`offline` or `--prefer-bundled`
only); versions are no longer pruned (the `time` map — the actual memory hog, one entry per
published version — is dropped instead); the range-selection rule lives in one place.

**And one finding that stops the fix from shipping:** with synthesised packuments refreshed to
real metadata (`JHOL_SOLVER_FULL_METADATA=1`), the solver *does* return an answer — `get-intrinsic
1.3.0` — but the tree is wrong in a different way: `accepts@2.0.0`, `array-flatten@3.0.0`,
`async-function` — express-5-era dependencies for an express-4 manifest. So the chart solver has
its own defect, and until it produces the tree the ranges describe, the estimate must stay the
resolver of record. That switch is therefore default-off and documented as such.

Scorecard after this pass: **unchanged** (`express` FAIL, `jest` FAIL, `esbuild` PASS, `sharp` FAIL).
No row improved; the work was to find why, and the two findings above are worth more than a
one-line version bump, because they name the two defects that actually decide tree identity.

## Second pass: 7 of 10 rows green, and the three that are not are named

Three fixes landed, each verified by the row it was written for:

1. **Synthesised packuments are refreshed at every insertion point** (`real_metadata_if_synth`), and
   the bundled snapshot refuses to exist while a registry is reachable. `[solve] refreshing 34
   synthesised packument(s)` → `0`.
2. **`normalise_selection`** re-derives every version from real metadata and the constraints that
   reached it, using the one rule (`pick_for_specs`). This is what turned `get-intrinsic` from
   1.3.1 into **1.3.0**.
3. **`prune_unreachable`** drops packages queued by a version that was later replaced — the
   `async-function` leaf that nothing needed.
4. **`selection_satisfies_declared_ranges`** makes the chart solver prove its answer before it may
   override the estimate. It surfaced a real chart defect in one line:
   *"express@4.18.2 declares accepts ~1.3.8, selection has 2.0.0"* — the chart's edge masks are
   unions across a package's versions, so it cannot respect per-version ranges. The solver is
   therefore never allowed to silently win; until it is version-aware, the estimate is authoritative.
5. **Peers are installed** (npm 7+ semantics), non-optional only.

## Third pass: 8 of 10 rows match npm

Two more fixes, both found by reading the failure rather than guessing:

- **Peers survive pruning.** `@types/react-dom` was kept but its peer `@types/react` (and its own
  `@types/prop-types`, `csstype`) was dropped: a selected peer is now kept regardless of whether
  the declaring edge is optional. `react-peers` PASSES.
- **`close_selection`** closes the selection under the dependencies its *final* versions declare.
  `normalise_selection` and `ensure_peers` can change a version after the estimate walked the
  graph, and a different version declares different dependencies — `pretty-format requires
  ansi-styles ^5.0.0, resolved <missing>` was that bug. The pass only **adds** what is missing:
  replacing a version would trade one violation for another when two parents need incompatible
  majors, which is the nested resolver's job. `sharp-native` PASSES with it.

Also: the install cache was corrupt (`SSDP publish error: Not a directory`) from the disk-full
runs; clearing `~/.jhol-cache` (4.8 GB) fixed it and brought the machine back to 5.3 GB free.

## Fourth pass: 9 of 10 rows match npm — and the tenth was a harness bug too

into `node_modules`, so a **nested copy** (`node_modules/@istanbuljs/load-nyc-config/node_modules/

That is the third time this harness has taught the same lesson: **a comparison that cannot see a

and `jest-29` PASSES.

## The last row, and why it is not a one-line fix

`babel-scoped` differs in one place: `@babel/preset-env@7.23.9` declares

```
"@babel/preset-modules": "0.1.6-no-external-plugins"
```

an **exact pin to a prerelease-tagged release**, while `0.1.6` (a plain release, lexically greater
than its own prerelease) is also published. We install `0.1.6`; npm installs the pinned string, and
because that version declares different dependencies it also pulls
`@babel/plugin-proposal-unicode-property-regex`, which npm's tree does not have. One decision
explains both diff lines.

An exact-pin enforcement at the selection layer was written and **reverted**: it made two other
rows fail, and the reason is the interesting part. The enforcement could not find the pinned
string among our candidate versions at that point — which points at the floor beneath it, not at
the chooser:

> the version list we hold for `@babel/preset-modules` appears to be missing
> `0.1.6-no-external-plugins` itself.

That is the next thing to measure, and it is a metadata question, not a selection question:
`registry::fetch_metadata` and the abbreviated-packument path need to be checked for whether
prerelease-tagged versions survive pruning, and for whether the `dist-tags`-driven fetch can return
a document whose `versions` object is filtered. Until that is answered, any chooser-level rule is a
patch on a symptom.

Recorded rather than papered over: **9/10 with the remaining failure localised to one exact pin and
one suspected metadata omission.**

## The last row: a wildcard test applied to the whole string

`is_exact_version_pin` rejected any spec containing the letter **x** anywhere, so every
prerelease-tagged pin whose name contains one — `0.1.6-no-e**x**ternal-plugins`, `-e**x**perimental`,
`-ne**x**t` — was read as a wildcard range and resolved by caret instead of exactly. That is why
`@babel/preset-env`'s pin of `@babel/preset-modules` installed `0.1.6` instead of the tagged release,
and why the tagged release's missing dependency (`@babel/plugin-proposal-unicode-property-regex`)
appeared in our tree. The wildcard test now applies to the **version core** only, before the first
hyphen. One rule, every dependent package.

After it: `babel-scoped`'s version difference is gone. What remains is `electron-to-chromium`
1.5.482 against npm's 1.5.483 — a package that publishes several times an hour. Our packument was
fetched before 1.5.483 existed; npm's was fetched after. The scorecard now retries such a row once
and reports `RETRY` with `REGISTRY-RACE`, never `PASS`, so the flake is visible rather than smoothed
away. The retry did not flip this row because the staleness is in our **persisted** packument, not
in the timing of a single run — the honest label is `REGISTRY-RACE`, and the product-level fix is a
bounded revalidation window for resolution metadata (npm has one; ours is generous).

Also fixed: `ensure_peers` fetched a peer's metadata but not the *declaring* package's, so peers
were silently skipped when the declarer's document was absent — the react-peers regression seen
with a cold cache.

Final: **nine rows PASS, one row REGISTRY-RACE**, and the pin defect that caused the tenth fixed at
its root.

## Following the last difference to the layer that still holds old data

`babel-scoped` differs on `electron-to-chromium` 1.5.482 against npm's 1.5.483. Chasing it one level
up removed the guessing:

| fact | measured |
|---|---|
| both trees have `browserslist` | **4.29.5** (identical) |
| npm's `browserslist@4.29.5` declares | `electron-to-chromium: ^1.5.464` |
| ours behaves as if it declared | `1.5.482`, exactly |
| the registry's `latest` for `electron-to-chromium` | **1.5.483**, present in the version list |

So the resolver was not wrong about the range; it was reading a **different document for the same
package version** — one fetched before 1.5.483 existed. In-memory freshness is now enforced
(`JHOL_METADATA_FRESHNESS_SECS`, default 60 s; `--as-of` and offline exempt), and
`get_cached_packument` refuses a stale entry. **The persisted packument cache is the remaining
layer**: `origin`'s disk reader still has its own TTL, and it is consulted before the network path,
so a stale file can still answer a resolution.

That is the exact next change, and it is one function: give the disk read the same freshness rule
(and honour ETag/Last-Modified when revalidating, which the write path already records).

Recorded instead of smoothed: nine rows PASS, one row explained down to "a stale on-disk packument",
with the freshness rule in place for the in-memory path that the scorecard exercises most.

Also corrected in this pass, from the same investigation: the lockfile writer stores **resolved exact
versions** in each package's `dependencies` map where npm stores the declared range. It is why a diff
looks like a one-patch drift when the choice was made two levels up, and why `jhol why` reads pins
where the registry has ranges. That is the next fidelity fix after the cache.

## The last layer: two freshness policies, and the one above the cache

`origin::within_metadata_ttl` kept its own TTL (3600 s) while the in-memory cache used another, so a
document could be fresh on disk and stale in memory **at the same instant** — and the disk one won,
because it is consulted first. That is the same bug class as the bundled-index snapshot: *a cache
deciding facts a cache cannot own*. Both layers now call one policy function
(`registry::metadata_freshness`: 60 s, `JHOL_PACKUMENT_TTL_SECS` override, `--as-of` and offline
exempt).

It did not change the `babel-scoped` row, and the reason is now measurable rather than mysterious: we
read the **abbreviated** packument during install (`application/vnd.npm.install-v1+json`), whose
`dist-tags` are served from a CDN edge, while `npm view` reads the **full** document. The abbreviated
copy can report `latest = 1.5.482` while the full one already says `1.5.483`. Two clients installing
seconds apart can therefore legitimately disagree — that is registry propagation, not resolution.

What that means for the product, stated without a workaround:

- the resolver is **correct** on the document it holds (nine rows prove the semantics);
- freshness is now enforced at both cache layers with one rule;
- the remaining difference is **document provenance** — abbreviated (fast, cached at the edge) versus
  full (authoritative). Choosing between them is a real design decision: use abbreviated for speed and
  accept propagation lag, or revalidate the abbreviated document against its `ETag` when a resolution
  is about to commit a version, and fall back to full when the two disagree.

That decision is the next step, and it belongs above the cache, not inside it.
