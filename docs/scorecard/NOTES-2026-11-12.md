## Root cause of the `express` failure (verified, not guessed)

```
$ npm view get-intrinsic dist-tags        → {"latest":"1.3.0"}
$ npm view get-intrinsic versions         → … 1.2.7, 1.3.0, 1.3.1
$ npm view get-intrinsic@1.3.1 deprecated → (none)
$ npm view side-channel-map@1.0.1 dependencies.get-intrinsic → ^1.2.5
$ npm view call-bound@1.0.4 dependencies.get-intrinsic       → ^1.3.0
```

Both dependents' ranges are satisfied by 1.3.0 **and** 1.3.1.

- **npm installs 1.3.0** — the version the `latest` dist-tag points at.
- **jhol installs 1.3.1** — the highest version satisfying the range.

1.3.1 is published but not tagged `latest`, and it is 1.3.1 that pulls `async-function` (and that,
`async-generator-function`). So one version choice explains both the extra packages and the file
count (+19 %).

**This is not a layout or installer bug. It is a version-selection policy difference**, and it is
the kind that cascades: a different `get-intrinsic` changes the tree, the file count and, for
native packages, which prebuilt binaries get pulled (`sharp` adds `@emnapi/runtime` for the same
reason).

## The rule this points to (ours, derived from the failure)

> When a range is satisfied by the version the registry's `latest` tag points at, prefer it.
> Only when `latest` does not satisfy the range, take the highest satisfying version.

Why it is right on its own terms, not because npm does it: a fresh install should reproduce what
`latest` promises. Choosing a published-but-untagged version means the tree depends on a release
the registry's own front page does not advertise — which is exactly how a fresh install differs
from the one every other tool produces.

**What this is not:** it is not porting npm's resolver. JAGR-∞ stays the resolver; this is one
preference inside candidate ordering, derived from an observed contract and provable with the
scorecard row that produced it.

## The `jest` failure is a different class

jhol installs 2 packages npm does not (`camelcase@5.3.1`, `semver@6.3.2` missing relative to npm).
Same suspicion — different version of an intermediate package eliminating or requiring a
transitive — but it must be verified the same way before any code changes. Not yet classified.

## Harness limitations found while using it

1. **Layout is invisible.** The manifest is a *set* of `name@version`, so two nested copies of
   1.3.0 and one flattened copy look identical. A later pass should record depth, not just
   identity. (Deliberately deferred: fix resolution first, layout second.)
2. **Extra files pass.** The file check only fails when jhol has < 95 % of npm's count, so the
   `esbuild` row passed while shipping 16 files against 11. Should become an absolute comparison
   once layout is recorded.
3. **Timing is informational only.** Cold npm and cold jhol hit the network differently; the
   column stays out of the verdict until semantics match.
4. **`--ignore-scripts` means lifecycle scripts are not yet compared.** Pass 2 must run with
   scripts enabled on the scenarios that build (sharp), and compare script presence and order.

## Order of work this establishes

1. Implement the `latest`-preference rule in candidate ordering; prove it with the `express` row.
2. Re-run the scorecard; classify what remains by reading the registry, never by guessing.
3. Add depth to the manifest, then make the file check absolute.
4. Pass 2 with scripts; compare presence/order on `sharp`.
5. Then the Linux gate: `docker run … sh scripts/scorecard.sh`.

No row is deleted because it fails, and no failure is "fixed" by loosening the comparison.
