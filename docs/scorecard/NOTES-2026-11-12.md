(`--ignore-scripts`) so resolution is compared before native builds can confuse it.

## Root cause of the `express` failure (verified, not guessed)

```
$ npm view get-intrinsic dist-tags        → {"latest":"1.3.0"}
$ npm view get-intrinsic versions         → … 1.2.7, 1.3.0, 1.3.1
$ npm view get-intrinsic@1.3.1 deprecated → (none)
$ npm view side-channel-map@1.0.1 dependencies.get-intrinsic → ^1.2.5
$ npm view call-bound@1.0.4 dependencies.get-intrinsic       → ^1.3.0
```

Both dependents' ranges are satisfied by 1.3.0 **and** 1.3.1.

- **npm installs 1.3.0** — the version the `latest` dist-tag points at.
- **jhol installs 1.3.1** — the highest version satisfying the range.

1.3.1 is published but not tagged `latest`, and it is 1.3.1 that pulls `async-function` (and that,
`async-generator-function`). So one version choice explains both the extra packages and the file
count (+19 %).

**This is not a layout or installer bug. It is a version-selection policy difference**, and it is
the kind that cascades: a different `get-intrinsic` changes the tree, the file count and, for
native packages, which prebuilt binaries get pulled (`sharp` adds `@emnapi/runtime` for the same
reason).

## The rule this points to (ours, derived from the failure)

> When a range is satisfied by the version the registry's `latest` tag points at, prefer it.
> Only when `latest` does not satisfy the range, take the highest satisfying version.

Why it is right on its own terms, not because npm does it: a fresh install should reproduce what
`latest` promises. Choosing a published-but-untagged version means the tree depends on a release
the registry's own front page does not advertise — which is exactly how a fresh install differs
from the one every other tool produces.

**What this is not:** it is not porting npm's resolver. JAGR-∞ stays the resolver; this is one
preference inside candidate ordering, derived from an observed contract and provable with the
scorecard row that produced it.

## The `jest` failure is a different class

jhol installs 2 packages npm does not (`camelcase@5.3.1`, `semver@6.3.2` missing relative to npm).
Same suspicion — different version of an intermediate package eliminating or requiring a

## Harness limitations found while using it

1. **Layout is invisible.** The manifest is a *set* of `name@version`, so two nested copies of
   1.3.0 and one flattened copy look identical. A later pass should record depth, not just
   identity. (Deliberately deferred: fix resolution first, layout second.)
2. **Extra files pass.** The file check only fails when jhol has < 95 % of npm's count, so the
   `esbuild` row passed while shipping 16 files against 11. Should become an absolute comparison
   once layout is recorded.
3. **Timing is informational only.** Cold npm and cold jhol hit the network differently; the
   column stays out of the verdict until semantics match.
4. **`--ignore-scripts` means lifecycle scripts are not yet compared.** Pass 2 must run with
   scripts enabled on the scenarios that build (sharp), and compare script presence and order.

## Order of work this establishes

1. Implement the `latest`-preference rule in candidate ordering; prove it with the `express` row.
2. Re-run the scorecard; classify what remains by reading the registry, never by guessing.
3. Add depth to the manifest, then make the file check absolute.
4. Pass 2 with scripts; compare presence/order on `sharp`.
5. Then the Linux gate: `docker run … sh scripts/scorecard.sh`.

No row is deleted because it fails, and no failure is "fixed" by loosening the comparison.

## Update: the rule is implemented, and it is not yet on the path that decides

The `latest`-preference is now in `packuments::pick_for_specs` (one rule, five tests) and used by
`jagr_nest::choose_version` and both `lockfile_write::resolve_*` helpers. **`express` still
resolves `get-intrinsic@1.3.1`**, so the rule is inert for installs. Evidence, not a guess:

```
$ JHOL_TRACE_PICK=1 jhol install      # fresh dir, express@4.18.2
[pick] jagr              237 calls
[pick] pick_for_specs    239 calls
```

476 version decisions, and **not one of them is `get-intrinsic`** — so its version is chosen by a
code path that never asks these helpers. Two facts point at where:

1. The lockfile records **exact pins** in parents' dependency maps
   (`side-channel-map@1.0.1 → get-intrinsic: "1.3.1"`), not the original `^1.2.5` the registry
   publishes. So by the time anything with a range runs, the choice may already be made.
2. The resolver expands candidates from "newest version" helpers
   (`packument::newest_version`, `collect_dep_names_for`'s `newest`) rather than from a
   range-selection call.

Next step is therefore narrow and named: make **candidate expansion** latest-aware in one place
(the newest-version helpers plus the ordinal where the lattice takes its max), not to add a sixth
range-selection helper. Until the `express` row changes, this note stays open and no claim is made
that it is fixed.

Correction to the earlier plan: "implement the rule and prove it with the express row" assumed a
single selection choke point. There are several, and the instrumented trace is how that was found
rather than assumed.

## The actual cause: the solver was being fed a snapshot, and the estimate became the resolver

The `latest`-tag rule was never going to matter, because `select_versions` **returns `None`** for
an ordinary `express@4.18.2` install. Instrumented bail reasons:

```
[solve] bail: propagate: JAGR-∞ conflict: no version of mime satisfies every dependent
        (candidates after narrowing: [1.6.0]); accepts needs mime…; send needs mime…; type-is needs mime…
[solve] chart returned None for get-intrinsic
```

And the packument the solver received:

```
[solve] input packuments=70 mime_versions=Some(1)
        mime_keys=Some(["_bundled_index_synth", "dist-tags", "name", "versions"])
```

`_bundled_index_synth` is a build-time snapshot with **one version per package**. A snapshot's
`mime@1.6.0` cannot satisfy `~1.2.6` *and* `0.19.0`, so propagation reports a conflict, the solver
declines, and the comment in `install.rs` applies: *"if the chart cannot be built or the solve
fails, the estimate stands."* The greedy estimate — built from the same snapshot — chose
`get-intrinsic@1.3.1`, which is what the world saw.

So three defects compound:

1. **A snapshot was used mid-resolution** for exact pins (`bundled_index_allowed` returned true when
   every constraint was a pin), so the estimate could feed itself from a stale version set.
2. **Packument version lists were pruned by "constraints seen so far"**, dropping versions a later
   dependent needed (`mime`), which made the solver's input unsound even without the snapshot.
3. **The solver was bypassed silently.** A failing solve was not reported, so a wrong tree shipped
   with no signal.

Fixed here: the snapshot no longer answers exact pins online (`offline` or `--prefer-bundled`
only); versions are no longer pruned (the `time` map — the actual memory hog, one entry per
published version — is dropped instead); the range-selection rule lives in one place.

**And one finding that stops the fix from shipping:** with synthesised packuments refreshed to
real metadata (`JHOL_SOLVER_FULL_METADATA=1`), the solver *does* return an answer — `get-intrinsic
1.3.0` — but the tree is wrong in a different way: `accepts@2.0.0`, `array-flatten@3.0.0`,
`async-function` — express-5-era dependencies for an express-4 manifest. So the chart solver has
its own defect, and until it produces the tree the ranges describe, the estimate must stay the
resolver of record. That switch is therefore default-off and documented as such.

Scorecard after this pass: **unchanged** (`express` FAIL, `jest` FAIL, `esbuild` PASS, `sharp` FAIL).
No row improved; the work was to find why, and the two findings above are worth more than a
one-line version bump, because they name the two defects that actually decide tree identity.
