# The Warm Path — Technical Report

**Date:** 2026-11-10 · **Scope:** install (warm, cold, daemon), `jhol fmt`, JholVM suite ·
**Method:** measure, change one thing, measure again; bash's `time` builtin only (no subprocess
in the delta); a package count taken after every run.

# Part I — The warm path

## 1.1 What a warm install is

```
main()
  restore_snapshot():  rename(.jhol/prepared-N → node_modules)      0.2 ms
  verify_tree():       71 manifests vs the lockfile                  3 ms
  summary
```

Everything else — cache lookup, resolution, projection — is skipped. The interesting work is
in three places: how the snapshot gets made, how it gets trusted, and what happens when it is
missing.

## 1.2 The snapshot: five invariants

A verified tree is kept as a copy-on-write clone under `.jhol/prepared-{1,2}`, with a marker
`.jhol/prepared-N.json` holding a hash of the **final** `package.json` and `package-lock.json`.

1. **Keyed on final inputs.** The fingerprint is computed after every write. The first version
   computed it inside `install_package`; the CLI then rewrote the lockfile, so the marker never
   matched and the snapshot was never used — the mechanism was correct and unreachable for
   days. *A cache keyed on inputs must be keyed on their final value.*
2. **Written last.** A rebuild deletes the marker first and writes it after the clone and its
   verification, so an interrupted rebuild leaves an unusable slot, never a half-filled one.
3. **Restored by `rename`.** `rename(2)` of a directory is instant on the same volume;
   `clonefile` of the same 738-file tree is 12–21 ms. The restore is a move, not a copy.
4. **Verified before trusted.** The moved-in tree is verified against the lockfile, and
   removed if it fails, so the fallback is a normal install.
5. **Two slots, and the consumed one refilled from its sibling** (§1.4).

## 1.3 The refill is a detached child, not a wait

Restoring consumes a slot. Rebuilding it costs 16–21 ms (one recursive `clonefile`) plus 3 ms
of verification. The user does not wait for it: `fork()` without `exec` — the child keeps the
already-loaded binary, does the clone, and `_exit`s.

Two failures were found here, both by measuring rather than reading:

* **`Command::spawn` cost 15 ms**, as much as the work it deferred: the parent waited for
  `fork` + `exec` + dynamic linking of a 17 MB binary. A bare `fork` is fractions of a
  millisecond. Safe only because the restore runs before the network prewarm thread is
  spawned, so the child is single-threaded and inherits no held locks.
* **The child inherited stdout.** `$(jhol install)`, `| tee`, CI capture and `execSync` all
  wait for EOF, so a piped caller waited for a clone it never asked for (45 ms piped against
  12 ms to a file). The child now calls `setsid` and points fds 0–2 at `/dev/null`.

## 1.4 The bug that made warm install alternate

Warm installs measured **11 ms / 45 ms / 11 ms / 45 ms**. The clone was not the problem, the
verification was not the problem, and the scheduler was not the problem. The refill copied
from the wrong place:

```
restore consumes slot A  →  fork refill  →  clone node_modules → A
                                             ^ the caller's next
                                               `rm -rf node_modules`
                                               deletes this mid-clone
```

The clone lost its source, the fill discarded the slot ("tree changed during snapshot"), and
the next run had nothing to restore. Every second run paid a full projection install.

Two corrections, both small:

* the fill verifies the **slot** (`tree_state::subtree_matches`), not the live tree. The slot
  is what will be restored; the live tree is what is about to be deleted. Verifying the wrong
  one threw away perfectly good snapshots.
* the consumed slot is refilled from its **sibling**, a directory nothing deletes.

| warm install, 71 packages, tree wiped | before | after |
|---|---:|---:|
| 400 ms idle | 11 / 45 alternating | **12–19 ms** |
| tight loop | 33–36 ms | **8–10 ms** |

The tight loop — the shape every benchmark uses — is now the **fastest** case, because a
sibling slot is always available and no clone ever races a delete.

## 1.5 What a warm install spends

`JHOL_PROFILE_STARTUP=1`, one restoring run:

| phase | time |
|---|---:|
| process-start → `main` | **4.3–6.9 ms** |
| config load | 0.05–0.2 ms |
| restore: fingerprint / slot search / rename / verify | 0.1 / 0.03 / 0.2 / 3.4 ms |
| freshness report | 1.6–2.3 ms |
| **total in the fast path** | **6–9 ms** |

Process start is now the largest single item, and it is at the platform floor: a
`rustc -O` hello-world takes 8 ms measured the same way, `jhol --version` 6 ms.

# Part II — The daemon never wins an install

Measured with the daemon warm and identical work either way:

| | native | `--daemon` |
|---|---:|---:|
| snapshot available | **10 ms** | 85–92 ms |
| no snapshot | **38 ms** | 122–137 ms |

Its own `install_package` is 15 ms and the socket round trip 12–18 ms; the rest is the second
process's post-install work (patch replay, engine scan, summary counts). There is no size at
which that layer pays for itself once a verified tree restores by `rename`.

So **installs stay in-process**. `--daemon` is accepted and honoured by taking the faster
path; `JHOL_DAEMON_INSTALL=1` restores delegation for experiments. The daemon keeps the jobs
it is good at: metadata cache and anticipatory prefetch. The flag also rides the fast gate —
keeping it off cost 81 ms against 10 ms.

# Part III — `jhol fmt`

## 3.1 It was already fast; the number was wrong

`fmt` is parallel (rayon) with a content-keyed cache. The "25 ms" in circulation was a **cold
first run** measured with a harness that added 18 ms.

| 55 files | jhol | bun |
|---|---:|---:|
| unchanged (cache hit) | **6–8 ms** | 7–8 ms |
| 44 of 55 rewritten | **9–10 ms** | 10–11 ms |
| `--check`, cold cache | 24 ms | — |

`--no-cache` is identical to the cached dirty run, so the cache write is not the cost. Both
figures sit at the process-start floor.

## 3.2 Two additions on top

* **Walk snapshots.** `.jhol/fmt-cache.json` records every directory walked with its mtime in
  ns, read **before** the directory was listed — an entry added during the walk can only make
  the snapshot stale, never wrong — plus the file list under the cache's own keys. `.jhol` is
  excluded because saving the cache rewrites it and would stale every snapshot.
* **A front-door lane in the trampoline.** `jhol-trampoline` answers `jhol fmt [--check] [dir]`
  itself when it can prove the full CLI would print `0 changed`: no other flags, in-process
  formatter extensions, no prettier config in cwd, and every file hashing to its cache entry.
  Measured 4.34 ms against 7.19 ms for 200 files / 26 directories; parity verified across 16
  scenarios (new file, new subdir, delete, rename, in-place edit, ignore files appearing) with
  zero differences.

The lane is a second implementation of one decision, which is a known hazard in this project.
The mitigation is the parity harness plus unit tests that pin the engine string and the
default config digest to values the CLI itself wrote.

# Part IV — JholVM: the suite under 100 ms

A suite total could not come from engine work: **eleven process starts cost ~88 ms** at the
platform floor, and `hello-world` alone is 8 ms. So the bottleneck was moved, not shaved.

`jhol run` now accepts several files and runs each with its **own engine in one process**:
the binary and engine infrastructure load once, globals and timers cannot leak between
scripts, and the exit code is the worst of the files.

| 11 benchmark scripts | before | after | bun |
|---|---:|---:|---:|
| wall | 140 ms (11 processes) | **88–90 ms** | 149–220 ms |

Verified: a `globalThis` set in file one is `undefined` in file two; a throwing file makes the
run exit non-zero; five tiny scripts cost 8 ms together against 23 ms separately.

# Part V — Cold install is the registry

Profiled with a fresh cache:

| stage | time |
|---|---:|
| 39 metadata fetches (`after_expansion`) | **749–1273 ms** |
| everything jhol does afterwards | **17 ms** |

The registry was answering in ~500 ms per request during that measurement. One duplicate *was*
ours: `express/4.18.2` fetched twice, 540 ms each, because the header and bearer download paths
bypassed the URL memo `get()` already had. Fixed for unauthenticated requests — two tokens can
legitimately see different bodies, so authenticated requests stay uncached.

Repeated fresh-cache runs: jhol 0.72–1.00 s, bun 0.75–1.04 s, npm 2.0–2.4 s. jhol and bun are
within each other's noise on cold because both wait on the same registry. **The 17 ms that is
ours cannot be the difference**, and saying otherwise would be an unearned claim.

# Part VI — Measurement discipline (the part that keeps being the bug)

Every wrong number this project has published came from the harness, not the code.

| harness defect | effect |
|---|---|
| `python3 -c 'time.time()'` run *after* the command | +18 ms to every reading, both directions; made bun look 2× slower than it is and `fmt` look 4× slower |
| cold page-in of a freshly built binary | first run 540–820 ms; interpreted as a code regression twice |
| suites run without `--all-features` | 26 `jhol-core` tests never executed by CI |
| `cargo test --test commands` not run | four real defects (link installs, workspace `ci`, backend probe, daemon deadlock) stayed invisible through green gates |
| `JHOL_CACHE_DIR` does not isolate the cache | cold comparisons contaminated by `~/.jhol-cache` and the 2.1 GB bundled packages; needs `HOME` redirected and packages outside the bundle |
| disk at 194 MB free | `errno=28` mid-build, twice, and `cp -cR`/`cargo` failures that looked like code errors |

Rules now written into `OPERATIONS.md`: time with the shell builtin; take a package count after
every run; medians of ≥5 with the spread; a benchmark that starts its timer by spawning a
process is timing the harness.

# Part VII — Negative results, kept

Each of these was implemented, measured, and reverted. They are here so nobody pays for them
twice.

| idea | measured | why it failed |
|---|---|---|
| whole-tree `cp -cR` | 114 ms | clones per file; the single recursive `clonefile` is 12–21 ms |
| per-file hardlink farm | ~0.4 ms/pkg | slower **and** shares inodes — an in-place edit corrupts the snapshot (the model-store trap) |
| `Command::spawn` for the refill | 15 ms | fork+exec+dyld as expensive as the work it deferred |
| parallel subtree clone | 10–14 ms vs 9–11 serial | metadata copy does not overlap |
| inline refill when consuming the last slot | 30–50 ms tight | moved background work into the foreground |
| single verification per process | −2 ms | real, but swamped by the refill race; unproven complexity |
| `strip` the binary | no size or startup change | already stripped |
| capping the prefetch frontier at 96 | worse on large cold installs | remainder fetched one request at a time |
| resolving after each fixed-size slice | 286 documents, 7.1 s | the over-approximating frontier kept feeding names |
| `--as-of` frontier fetch | 6.8–10.6 s vs a 4.06–8.00 s baseline | network variance made the comparison meaningless |

# Part IX — Reproducing every number

```sh
# warm install (tight loop)
cd /tmp/proj && printf '{"name":"t","version":"1.0.0","dependencies":{"express":"4.18.2"}}' > package.json
jhol install >/dev/null            # first run builds the snapshot
for i in 1 2 3; do rm -rf node_modules; TIMEFORMAT='%3R'; time jhol install >/dev/null; done

# where a warm install spends its time
JHOL_PROFILE_STARTUP=1 jhol install    # [boot] and [startup] marks

# why a snapshot was or was not used
cargo run -p jhol-core --example snapshot_probe

# what a clone really costs
cargo run -p jhol-core --example clone_probe -- node_modules /tmp/probe
cargo run -p jhol-core --example verify_probe -- . 20

# the engine suite in one process
JHOL_RUNTIME_ENGINE=jholvm jhol run crates/jhol-vm/bench/*.js

# the whole gate
sh scripts/verify-all.sh
ROUNDS=10 sh scripts/verify-all.sh     # flake hunt
```

# Part X — What is left

1. **Process start (4.3–6.9 ms)** is now the largest single cost of a warm install, and it is
   the platform floor — but not necessarily ours: ~0.85 ms is loading
   JavaScriptCore/CoreServices/CoreFoundation for commands that never run JS, plus ~800 page
   faults from an 18 MB image. Splitting the CLI so `install`, `fmt`, `verify` and `cache` do
   not link a JavaScript engine is a linker-level change and the obvious next lever.
2. **Cold install** is the registry. Nothing in our 17 ms can change it.
3. **fmt** is at its floor; the remaining trick is the trampoline lane, which only applies when
   the trampoline is installed as `jhol`.
4. **Linux and Windows have never been executed.** No amount of local measurement changes that.
5. **~177 `JHOL_*` knobs** remain, three retired; each other one needs the same proof.
